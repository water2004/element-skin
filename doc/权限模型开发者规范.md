# Element Skin 权限模型开发者规范

> 状态：现行规范
>
> 目标读者：站点前端、后端贡献者、OAuth / 第三方应用开发者、启动器与外部工具作者、站点管理员
>
> 参考代码快照：`dev`，2026-08-06

## 1. 目标与边界

权限系统是站点所有受保护操作的唯一安全边界。所有需要授权的业务操作必须携带 `PermissionActor`，业务层必须使用 `PermissionActor` 的有效权限集合与 scope resolver 判定操作是否允许。

本文档定义 Element Skin 当前生效的权限模型。它不是草案，也不是实施排期说明。站点 API、OAuth/OIDC 授权页、外部身份、正版角色绑定、管理后台权限编辑和 Yggdrasil 会话都必须遵循本文档。

规范要求：

- 每个站内用户必须拥有一个 `PermissionSubject`。
- 每个受保护业务操作必须携带一个 `PermissionActor`。
- 权限判断必须位于 service 层或 service 调用的权限模块中。
- 路由层不得直接散落角色判断、管理员判断、超级管理员判断。
- 数据库层不得做权限判断。
- 受保护主体不得绕过权限检查；前端可将 `protected = true` 的管理员展示为“超级管理员”，但后端不再存在 `super_admin` 角色预设。
- 站内网页登录、外部 OIDC 身份、本站 OAuth/OIDC、正版角色绑定和 Yggdrasil 必须归一到同一套 `PermissionSubject` / `PermissionActor` 模型。
- 委托访问不得绑定角色；委托访问只能使用逐项授权的 Permission 集合。
- `is_admin`、`is_super_admin`、裸 `user_id` 传递不得作为权限接口。
- 权限数据必须结构化存储，禁止使用 JSON 字符串承载权限、scope、授权范围或策略。

权限模型只回答一个问题：

```text
当前 PermissionActor 是否能在当前会话入口下，对指定资源执行指定操作。
```

权限模型不负责参数校验、业务状态流转、数据库事务封装、页面展示。

### 1.1 第三方开发者契约

第三方应用和外部工具只应依赖以下稳定外部概念：

| 概念 | 外部稳定性 | 说明 |
| --- | --- | --- |
| `permission.code` | 稳定 | OAuth scope、授权页、审计、错误提示和开发者文档使用的权限码 |
| `resource.action.scope` | 稳定 | 权限码格式，三段含义固定 |
| scope 语义 | 稳定 | `self`、`owned`、`bound_profile`、`public`、`assigned`、`server`、`any`、`system` 的判定语义固定 |
| `PermissionActor` 行为 | 稳定 | 一次请求只能使用 Actor 中实际存在的权限 |
| 委托授权交集规则 | 稳定 | 第三方应用权限不得超过用户有效权限、应用允许权限、用户授权权限三者交集 |

第三方应用不得依赖以下内部实现细节：

| 概念 | 说明 |
| --- | --- |
| `permission.id` | 结构化整数 ID，仅用于数据库关联、缓存和内部一致性校验 |
| `permission.bit_index` | 运行时 bitset 位序，仅用于服务端权限计算 |
| 内置角色名称 | OAuth 和第三方委托授权不得申请角色，只能申请逐项 Permission |
| 数据库表结构 | 表结构用于解释权限模型事实来源，不作为外部远程调用接口 |

第三方应用申请站点能力时，必须使用 `permission.code` 作为授权项。用户批准后，应用拿到的访问令牌只能调用同一套站点 API；后端会把令牌解析成 `PermissionActor` 并执行同样的权限检查。

## 2. 核心对象

### 2.1 PermissionSubject

`PermissionSubject` 表示用户、应用客户端或系统任务的长期权限身份。

字段定义：

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | TEXT | PRIMARY KEY | 权限主体 ID |
| `kind` | TEXT | `user` / `client` / `system` | 主体类型 |
| `user_id` | TEXT | 用户主体唯一，客户端和系统主体为空 | 关联用户 |
| `status` | TEXT | `active` / `disabled` / `locked` | 主体状态 |
| `protected` | BOOLEAN | NOT NULL | 是否为受保护主体 |
| `created_at` | BIGINT | NOT NULL | 创建时间 |
| `updated_at` | BIGINT | NOT NULL | 更新时间 |

状态规则：

- `active`：主体可参与权限计算。
- `disabled`：主体有效权限集合为空。
- `locked`：主体有效权限集合为空。

账号封禁不等同于 `PermissionSubject.status`。账号封禁属于账号制裁状态，必须参与会话入口策略。当前封禁语义只禁止 Yggdrasil `join` 与 `hasJoined` 代表的服务器加入链路。

客户端主体 ID 必须固定为：

```text
client:{client_id}
```

客户端主体只用于 Client Credentials 和受审核外置插件场景，不得代表用户，不得使用 `self`、`owned`、`bound_profile` 等依赖用户上下文的权限。

`protected` 是主体属性，不是权限，也不是角色。它用于标记受保护用户主体。普通管理员不得修改受保护主体所属账号；拥有 `permission_protected.manage.any` 的受保护主体可以把受保护状态转让给另一个用户主体。转让后旧主体 `protected = false`，目标主体 `protected = true`。

### 2.2 PermissionActor

`PermissionActor` 表示一次请求在特定会话入口下实际可用的权限身份。

字段定义：

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `subject_id` | TEXT | NOT NULL | 权限主体 ID |
| `user_id` | TEXT | 用户 actor 必填，客户端 actor 为空 | 归属用户 |
| `session_kind` | TEXT | NOT NULL | 会话种类 |
| `entrypoint` | TEXT | NOT NULL | 入口名称 |
| `session_id` | TEXT | 可为空 | 会话、token、state 或任务 ID |
| `bound_profile_id` | TEXT | 可为空 | Yggdrasil 绑定角色 |
| `delegation_id` | TEXT | 可为空 | 委托授权 ID |
| `delegated_client_id` | TEXT | 可为空 | 委托客户端 ID |
| `permissions` | PermissionBitSet | NOT NULL | 本次请求可用权限位图 |

公开端点同样必须携带 `PermissionActor`。请求未携带 Cookie 或 OAuth Bearer token 时，认证层构造运行时 `GuestActor`：

```text
subject_id = guest:public
user_id = null
session_kind = guest
entrypoint = public
permissions = 所有 scope=public 的权限
```

`GuestActor` 不对应 `permission_subjects` 数据库记录，不具有角色、主体覆盖或委托关系，也不参与下列数据库权限计算公式。它只用于让公开读取能力进入与登录用户相同的 service 权限检查。请求携带有效凭证时必须使用该凭证解析出的真实 Actor；真实 Actor 的 deny 覆盖可以拒绝公开权限。请求携带无效凭证时必须返回 `401`，不得降级为 `GuestActor`。

`PermissionActor.permissions` 的计算公式固定为：

```text
subject_effective_bitset
& session_permission_bitset(session_kind, entrypoint)
& delegation_permission_bitset(delegation_id)
& client_credentials_permission_bitset(session_id)
&^ account_sanction_denied_bitset(user_id, session_kind, entrypoint)
```

`delegation_id IS NULL` 时，`delegation_permission_policy` 返回全集。`delegation_id IS NOT NULL` 时，`delegation_permission_policy` 只能返回用户逐项授予且客户端被允许申请的权限集合。

### 2.3 Permission

`Permission` 是最小授权单元。

权限拥有两个稳定标识：

| 标识 | 用途 |
| --- | --- |
| `id` | 数据库关联、缓存、结构化权限编码 |
| `code` | 人类可读、审计、管理界面、种子数据 |

`code` 命名格式固定为严格三段：

```text
resource.action.scope
```

`resource`、`action`、`scope` 字段必须结构化存储。系统不得通过 split `code` 解析结构。

`resource` 使用小写英文和下划线，不得包含点号。

字段定义：

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | BIGINT | PRIMARY KEY | 结构化权限整数 ID |
| `code` | TEXT | UNIQUE | 人类可读稳定权限码 |
| `bit_index` | INTEGER | UNIQUE | 运行时稠密 bitset 位序 |
| `resource_id` | INTEGER | NOT NULL | 资源编号 |
| `action_id` | INTEGER | NOT NULL | 动作编号 |
| `scope_id` | INTEGER | NOT NULL | 作用范围编号 |
| `description` | TEXT | NOT NULL | 权限说明 |
| `created_at` | BIGINT | NOT NULL | 创建时间 |

`code` 必须等于 `resource + "." + action + "." + scope_id`。

`id` 使用 64-bit 结构化整数编码并存入数据库 `BIGINT`。数据库使用 PostgreSQL signed `BIGINT`，因此最高位不得使用，保证所有权限 ID 都落在正数范围内稳定存储。

编码布局固定为：

```text
reserved/category resource action scope
16 bits           16 bits  16 bits 16 bits
```

编码公式固定为：

```text
permission_id =
  resource_id << 32 |
  action_id   << 16 |
  scope_id
```

当前版本不启用 `reserved/category` 段，该段必须为 `0`。保留段仍然是物理布局的一部分，权限 ID 的完整布局始终是 `16 * 4`。

约束：

```text
0 < resource_id <= 65535
0 < action_id <= 65535
0 < scope_id <= 65535
reserved/category == 0
```

`resource_id`、`action_id`、`scope_id` 必须由种子数据固定分配。不得使用数据库自增 ID 作为 permission id。

`id` 与 `code` 必须互相校验：

```text
id.resource_id == permission_resources.id
id.action_id == permission_actions.id
id.scope_id == permission_scopes.id
code == resource.code + "." + action.code + "." + scope.code
```

运行时不得用字符串集合做权限计算。权限集合必须编译为 bitset：

```text
permission_bitset[permission.bit_index] = 1
```

`bit_index` 是稠密连续位序，只服务运行时 bitset。`bit_index` 不得等于 `id`，不得参与审计和外部接口。

权限判断固定为整数位运算：

```text
Has(actor.permissions, permission_id)
```

### 2.4 Role

`Role` 是权限主体的权限集合模板。业务层不得判断角色，只能判断权限。

字段定义：

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | TEXT | PRIMARY KEY | 角色 ID |
| `name` | TEXT | UNIQUE | 展示名称 |
| `description` | TEXT | NOT NULL | 角色说明 |
| `system_role` | BOOLEAN | NOT NULL | 系统内置角色 |
| `protected` | BOOLEAN | NOT NULL | 是否为受保护内置角色 |
| `created_at` | BIGINT | NOT NULL | 创建时间 |
| `updated_at` | BIGINT | NOT NULL | 更新时间 |

内置角色不得删除。内置角色的权限变更必须写入审计日志。

同一个 `PermissionSubject` 能绑定多个角色。主体有效权限由所有角色权限与主体覆盖项合并得到。

角色只能绑定到 `PermissionSubject`。委托访问、外部客户端、临时 state、access token 不得绑定角色。

### 2.5 DelegatedClient

`DelegatedClient` 表示一个第三方应用或外部工具。应用记录本身不是 `PermissionSubject`，不得直接绑定角色。

Client Credentials 场景必须为应用创建独立权限主体 `client:{client_id}`。该主体可以被管理员逐项授予允许的 app-only permission，但不得通过用户委托授权获得权限。

字段定义：

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | TEXT | PRIMARY KEY | OAuth client_id |
| `owner_user_id` | TEXT | NOT NULL | 应用创建者 |
| `name` | TEXT | NOT NULL | 应用名称 |
| `description` | TEXT | NOT NULL | 应用说明 |
| `redirect_uri` | TEXT | NOT NULL | 固定回调地址 |
| `website_url` | TEXT | 可为空 | 应用网站 |
| `client_type` | TEXT | `public` / `confidential` | 客户端类型 |
| `secret_hash` | TEXT | confidential 必填 | client_secret 哈希 |
| `status` | TEXT | `pending` / `active` / `rejected` / `disabled` | 应用审核与启用状态 |
| `created_at` | BIGINT | NOT NULL | 创建时间 |
| `updated_at` | BIGINT | NOT NULL | 更新时间 |

`delegated_client_permissions` 表示该应用申请并允许使用的 Permission 集合。该表保留历史命名，但语义不是“仅用户委托权限”。普通开发者创建或更新应用时，可以申请自己当前拥有的非 `system` 权限。`server` scope 只能由机密应用申请，只能用于 Client Credentials app-only token；公开应用不得申请 `server` scope。`system` scope 永远不能由第三方应用申请。用户授权结果必须写入 `DelegatedPermissionGrant` 和 `delegated_grant_permissions`。

应用创建者权限或角色变化后，服务端必须重新检查该创建者提交的 `pending` / `active` 应用。若应用申请的非 `server` 权限不再是创建者当前有效权限的子集，应用必须被置为 `disabled`。仍然满足条件的应用必须保持原状态。

### 2.6 DelegatedPermissionGrant

`DelegatedPermissionGrant` 表示用户把部分权限逐项授予某个客户端。它不是角色，也不得引用角色。

字段定义：

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | TEXT | PRIMARY KEY | 委托授权 ID |
| `user_id` | TEXT | NOT NULL | 授权用户 |
| `subject_id` | TEXT | NOT NULL | 授权用户的权限主体 |
| `client_id` | TEXT | NOT NULL | 客户端 ID |
| `status` | TEXT | `active` / `revoked` | 授权状态 |
| `created_at` | BIGINT | NOT NULL | 创建时间 |
| `revoked_at` | BIGINT | 可为空 | 撤销时间 |

委托访问的最终权限必须满足：

```text
PermissionActor.permissions bitset
<= subject_effective_bitset
PermissionActor.permissions bitset
<= client_allowed_permission_bitset
PermissionActor.permissions bitset
<= delegated_grant_permission_bitset
```

用户权限覆盖项或角色变化后，服务端必须重新检查该用户的 active grant。若 grant 中任一授权权限不再属于用户当前有效权限，或不再属于应用允许权限集合，grant 必须被置为 `revoked` 并写入 `revoked_at`。仍然满足条件的 grant 必须保持 active。

### 2.7 PermissionScope

`PermissionScope` 定义权限范围及 resolver。scope 必须先登记后使用。

首批 scope 固定为：

| scope | resolver_key | 语义 |
| --- | --- | --- |
| `self` | `subject_user` | actor 操作自己的账号级资源 |
| `owned` | `resource_owner` | actor 操作归属于自己的业务资源 |
| `bound_profile` | `session_bound_profile` | actor 操作当前会话绑定的角色 |
| `public` | `resource_public` | actor 读取公开资源 |
| `assigned` | `resource_assignment` | actor 操作明确分配给自己的资源 |
| `server` | `client_server` | 受审核的服务端或外置插件客户端执行服务器侧能力 |
| `any` | `global` | actor 操作任意用户或全站资源 |
| `system` | `system_actor` | 系统主体执行维护任务 |

`self` 和 `any` 不足以覆盖站点权限。`owned`、`bound_profile`、`public`、`assigned`、`server`、`system` 必须从第一版进入模型。

## 3. Scope Resolver 规则

### 3.1 `subject_user`

输入：

```text
actor.user_id
resource.user_id
```

通过条件：

```text
actor.user_id == resource.user_id
```

适用资源：

```text
account
```

### 3.2 `resource_owner`

输入：

```text
actor.user_id
resource.owner_user_id
```

通过条件：

```text
actor.user_id == resource.owner_user_id
```

适用资源：

```text
profile
texture
wardrobe
notice
yggdrasil_session
external_identity
official_profile
```

### 3.3 `session_bound_profile`

输入：

```text
actor.user_id
actor.bound_profile_id
profile.id
profile.user_id
```

通过条件：

```text
actor.bound_profile_id IS NOT NULL
AND actor.bound_profile_id == profile.id
AND actor.user_id == profile.user_id
```

适用资源：

```text
profile
texture application target
yggdrasil_server join target
```

### 3.4 `resource_public`

输入：

```text
resource.public
resource.enabled
```

通过条件：

```text
resource.public == true
AND resource.enabled == true
```

适用资源：

```text
texture
profile lookup result
site public setting
```

### 3.5 `resource_assignment`

输入：

```text
actor.subject_id
assignment.subject_id
assignment.resource_id
```

通过条件：

```text
assignment.subject_id == actor.subject_id
AND assignment.resource_id == resource.id
AND assignment.status == 'active'
```

适用资源：

```text
moderation task
review queue item
```

### 3.6 `client_server`

输入：

```text
actor.subject_id
actor.session_kind
client_server_binding.client_id
client_server_binding.status
```

通过条件：

```text
actor.subject_id == "client:" + client_server_binding.client_id
AND actor.session_kind == "client_credentials"
AND client_server_binding.status == 'active'
```

适用资源：

```text
minecraft_session server-side verification
external plugin server capability
```

`server` scope 不表示全站管理员能力，不得被用户委托 OAuth token 使用。它只适用于 Client Credentials 场景，由管理员审核后授予 `client:{client_id}` 主体。

### 3.7 `global`

输入：

```text
actor.permissions
```

通过条件：

```text
actor.permissions contains requested permission
```

`global` 不检查资源归属。

### 3.8 `system_actor`

输入：

```text
actor.subject.kind
actor.session_kind
```

通过条件：

```text
actor.subject.kind == 'system'
AND actor.session_kind == 'system'
```

普通用户和管理员不得使用 `system` scope。

## 4. Permission 目录

### 4.0 粒度规则

Permission 必须对应一个可独立授权、可独立撤销、可独立审计的业务能力。

禁止把安全语义不同的字段合并到同一个 `update` 权限中。一个操作同时修改多个安全语义时，service 必须分别检查对应 Permission。

当前必须拆分的高风险能力：

```text
材质备注、材质模型等普通元数据修改：texture.update_metadata.*
材质公开状态修改：texture.update_visibility.*
角色基础资料修改：profile.update.*
角色当前材质修改：texture.apply.* / texture.clear.*
账号展示资料修改：account.update.*
账号密码修改：account_password.update.*
```

委托访问授权页面必须展示 Permission 粒度的授权项，不得展示角色。

### 4.1 account

| Permission | 说明 |
| --- | --- |
| `account.read.self` | 读取自己的账号资料 |
| `account.update.self` | 修改自己的账号展示资料；向新邮箱发送验证码并在验证后重设自己的邮箱 |
| `account_password.update.self` | 修改自己的密码 |
| `account.delete.self` | 注销自己的账号 |
| `account.ban.any` | 封禁任意账号 |
| `account.unban.any` | 解除任意账号封禁 |
| `account.read.any` | 读取任意账号资料 |
| `account.update.any` | 修改任意账号资料 |

### 4.2 user

| Permission | 说明 |
| --- | --- |
| `user.read.any` | 管理后台读取用户列表和详情 |
| `user.update.any` | 管理后台修改用户基础信息 |

### 4.3 profile

| Permission | 说明 |
| --- | --- |
| `profile.read.owned` | 读取自己的角色 |
| `profile.create.owned` | 创建自己的角色 |
| `profile.update.owned` | 修改自己的角色 |
| `profile.delete.owned` | 删除自己的角色 |
| `profile.read.bound_profile` | 读取当前 Yggdrasil token 绑定角色 |

### 4.18 oauth_grant

| Permission | 说明 |
| --- | --- |
| `oauth_grant.read.owned` | 读取自己授予第三方应用的授权 |
| `oauth_grant.revoke.owned` | 撤销自己授予第三方应用的授权 |
| `oauth_grant.read.any` | 管理后台读取任意 OAuth 授权 |
| `oauth_grant.revoke.any` | 管理后台撤销任意 OAuth 授权 |
| `oauth_grant.revoke.system` | 系统维护任务撤销失去有效凭证的 OAuth 授权 |
| `oauth_grant.delete.system` | 系统维护任务删除已撤销 OAuth 授权 |

撤销授权时不得物理删除 grant。服务端必须写入 `status='revoked'` 与 `revoked_at`，并让后续 token 校验立即失效。已撤销 grant 保留 30 天用于用户可见历史和排错审计，30 天后由系统维护 actor 使用 `oauth_grant.delete.system` 删除 grant 及其授权码、refresh token、授权权限关联记录。

active grant 超过 10 分钟签发保护期后，如果没有未撤销且未过期的 refresh token，也没有仍在有效期内的 authorization code，系统维护 actor 必须使用 `oauth_grant.revoke.system` 自动撤销该 grant。refresh token 过期且未轮换后，第三方应用必须重新取得用户授权。authorization code 在有效期内即视为仍可能完成 token 兑换，即使兑换事务已经标记其为 consumed，也必须保留到原始过期时间以避免并发清理误伤。

权限变动必须向被影响用户发送系统通知。角色授权、角色撤销、单项权限覆盖新增、单项权限覆盖移除、受保护权限主体转移，都属于用户权限变动。通知必须由系统维护 actor 通过通知系统创建，类型为 `system`，受众为 `targeted`，`created_by` 为空，有效期 30 天。

权限变动引发的 OAuth 依赖校正也必须通知用户。授权用户失去某项已授权权限时，对应 active grant 必须自动标记为 `revoked` 并向授权用户发送系统通知。应用创建者失去某项应用已申请且创建者必须持有的权限时，对应应用必须自动变为 `disabled` 并向应用创建者发送系统通知。未受影响的 grant 和应用不得产生通知或状态变化。

## 7. Yggdrasil 权限流程

### 7.1 authenticate

流程固定为：

```text
1. 校验 username/password。
2. 定位 user。
3. 定位 PermissionSubject。
4. 构造 session_kind=yggdrasil、entrypoint=authserver 的 PermissionActor。
5. 检查 subject.status == active。
6. 检查 yggdrasil_session.create.owned。
7. 查询可用 profile。
8. 按现有 Yggdrasil 规则确定 selectedProfile。
9. 如果 selectedProfile 存在，检查 profile.read.owned。
10. 创建 access token。
```

失败规则：

- 凭据错误返回 Yggdrasil `ForbiddenOperationException`。
- 主体不存在、disabled、locked 返回 Yggdrasil `ForbiddenOperationException`。
- 权限不足返回 Yggdrasil `ForbiddenOperationException`。
- 任一步失败不得创建 token。

### 7.2 refresh

流程固定为：

```text
1. 读取 access token。
2. 校验 clientToken。
3. 根据 token.user_id 定位 PermissionSubject。
4. 构造 session_kind=yggdrasil、entrypoint=authserver 的 PermissionActor。
5. 检查 subject.status == active。
6. 检查 yggdrasil_session.refresh.owned。
7. 如果 token 已绑定 profile，检查 profile 仍属于 token.user_id。
8. 如果请求选择 profile，检查 token 当前未绑定 profile。
9. 检查被选择 profile 属于 token.user_id。
10. 轮换 access token。
```

失败规则：

- 权限、主体状态失败不得产生新 token。
- profile 所属关系失败必须使 refresh 失败。
- refresh 成功后旧 token 必须失效。

### 7.3 validate

流程固定为：

```text
1. 读取 access token。
2. 校验 clientToken。
3. 检查 token 未过期。
4. 根据 token.user_id 定位 PermissionSubject。
5. 构造 session_kind=yggdrasil、entrypoint=authserver 的 PermissionActor。
6. 检查 subject.status == active。
7. 检查 yggdrasil_session.validate.owned。
8. 如果 token 已绑定 profile，检查 profile 仍属于 token.user_id。
```

### 7.4 invalidate / signout

`invalidate` 流程固定为：

```text
1. 读取 access token。
2. 构造 session_kind=yggdrasil、entrypoint=authserver 的 PermissionActor。
3. 检查 yggdrasil_session.invalidate.owned。
4. 删除指定 token。
```

`signout` 流程固定为：

```text
1. 校验 username/password。
2. 定位 PermissionSubject。
3. 构造 session_kind=yggdrasil、entrypoint=authserver 的 PermissionActor。
4. 检查 yggdrasil_session.signout.owned。
5. 删除该用户全部 Yggdrasil token。
```

### 7.5 join

`join` 是服务器登录授权操作，必须进行权限检查。

流程固定为：

```text
1. 读取 access token。
2. token.ProfileID 必须存在。
3. token.ProfileID 必须等于请求 selectedProfile。
4. 根据 token.user_id 定位 PermissionSubject。
5. 构造 session_kind=yggdrasil、entrypoint=sessionserver_join 的 PermissionActor。
6. actor.bound_profile_id = token.ProfileID。
7. 检查 subject.status == active。
8. PermissionActor 构造阶段根据 users.banned_until 移除 yggdrasil_server.join.bound_profile。
9. 检查 profile 仍属于 token.user_id。
10. 执行 RequireScoped(actor, yggdrasil_server.join.bound_profile, profile)。
11. 写入 join session。
```

失败规则：

- token 缺失、未绑定 profile、profile 不匹配、profile 不再属于用户，全部返回 Yggdrasil `Invalid token`。
- subject disabled、locked、权限不足、账号封禁导致权限被移除，全部不得写入 join session。
- 账号封禁返回 Yggdrasil `ForbiddenOperationException`，消息固定为账号被封禁。

### 7.6 hasJoined

`hasJoined` 是 join 授权结果查询，不是公开绕过口。它必须复原 join 时的 actor，并通过 actor permissions 重新确认服务器加入授权仍然有效。

流程固定为：

```text
1. 通过 serverID 读取 join session。
2. join session 不存在或过期，返回 204。
3. 通过 join session.access_token 读取 access token。
4. token 不存在，返回 204。
5. token.ProfileID 必须存在。
6. 读取 profile。
7. profile 必须存在。
8. profile.id 必须等于 token.ProfileID。
9. profile.user_id 必须等于 token.user_id。
10. profile.name 必须等于请求 username。
11. 根据 token.user_id 定位 PermissionSubject。
12. 构造 session_kind=yggdrasil_join_grant、entrypoint=sessionserver_hasjoined 的 PermissionActor。
13. actor.bound_profile_id = token.ProfileID。
14. 检查 subject.status == active。
15. PermissionActor 构造阶段根据 users.banned_until 移除 yggdrasil_server.hasjoined.bound_profile。
16. 执行 RequireScoped(actor, yggdrasil_server.hasjoined.bound_profile, profile)。
17. 返回已签名的 profile payload。
```

失败规则：

- join session、token、profile、username 任一不匹配，返回 204。
- 账号封禁返回 Yggdrasil `ForbiddenOperationException`，消息固定为账号被封禁。
- subject disabled、locked 或权限不足返回 Yggdrasil `ForbiddenOperationException`。

### 7.7 Yggdrasil 材质接口

上传材质流程固定为：

```text
1. 读取 Bearer token。
2. token.ProfileID 必须等于 URL uuid。
3. 读取 profile。
4. profile.user_id 必须等于 token.user_id。
5. 构造 session_kind=yggdrasil、entrypoint=texture 的 PermissionActor。
6. actor.bound_profile_id = token.ProfileID。
7. 检查 subject.status == active。
8. 执行 RequireScoped(actor, texture.apply.bound_profile, profile)。
9. 处理上传文件。
10. 写入材质库。
11. 应用到绑定角色。
```

删除材质流程固定为：

```text
1. 读取 Bearer token。
2. token.ProfileID 必须等于 URL uuid。
3. 读取 profile。
4. profile.user_id 必须等于 token.user_id。
5. 构造 session_kind=yggdrasil、entrypoint=texture 的 PermissionActor。
6. actor.bound_profile_id = token.ProfileID。
7. 检查 subject.status == active。
8. 执行 RequireScoped(actor, texture.clear.bound_profile, profile)。
9. 清除绑定角色材质。
```

## 8. 外部身份与正版角色权限流程

外部身份是登录和外部能力授权的长期资源；正版角色绑定是另一个独立的本站资源。两者都复用现有用户 `PermissionSubject`，不创建新的权限主体。

### 8.1 OIDC login

流程固定为：

```text
1. guest 或已登录 actor 检查 identity_provider.read.public。
2. provider 必须 enabled 且 login_enabled。
3. 创建一次性 OIDC state、nonce 和 PKCE verifier。
4. callback 校验并一次性消费 state。
5. 已存在的 (provider_id, subject) 只能恢复其已关联用户。
6. 未存在且允许注册时只创建 identity_ticket，不创建本站账户。
7. 完整本站注册成功后才原子创建用户主体与外部身份。
```

OIDC claim 不授予本站 permission，不按 email 自动匹配用户，也不替代注册表单字段。

### 8.2 OIDC link 与重新授权

流程固定为：

```text
1. 当前请求必须有 user_id。
2. 检查 external_identity.create.owned。
3. 将 user_id 写入一次性 state。
4. callback 中 subject 已属于其他用户时返回冲突。
5. 未指定 `identity_id` 时，subject 已属于当前用户则更新同一身份，否则创建新身份，允许同 provider 多身份。
6. 指定 `identity_id` 时只能更新该用户、该 provider 下的目标身份；callback subject 不匹配时返回冲突，不得新增身份。
```

读取、修改标签和删除身份分别检查 `external_identity.read.owned`、`external_identity.update.owned` 和 `external_identity.delete.owned`。被正版绑定引用的身份不得删除。

### 8.3 正版绑定与同步

创建绑定固定为：

```text
1. 检查 official_profile.create.owned。
2. identity.user_id 与 profile.user_id 必须等于 actor.user_id。
3. identity provider 必须使用 microsoft adapter。
4. 按需取得外部 access token，并读取远端 Minecraft profile。
5. 只建立 official_profile_binding，不修改本站 profile。
```

显式同步固定为：

```text
1. 检查 official_profile.refresh.owned。
2. 重新验证绑定和资源归属。
3. 按需刷新外部 token；不得由定时任务提前刷新。
4. 下载并校验远端皮肤、披风。
5. 在事务中更新 profile、材质库和 last_synced_at。
```

解除绑定检查 `official_profile.delete.owned`，只删除绑定；不得删除 profile 或已同步材质。读取绑定检查 `official_profile.read.owned`。任何外部请求、图片或事务失败均不得留下部分业务状态。

## 9. 账号封禁模型

账号封禁使用结构化字段：

```text
users.banned_until
```

封禁语义：

- `banned_until IS NULL`：未封禁。
- `banned_until <= now`：封禁已过期。
- `banned_until > now`：封禁生效。

封禁生效时必须拒绝：

```text
yggdrasil_server.join.bound_profile
yggdrasil_server.hasjoined.bound_profile
```

封禁不移除：

```text
yggdrasil_session.create.owned
yggdrasil_session.refresh.owned
yggdrasil_session.validate.owned
yggdrasil_session.invalidate.owned
yggdrasil_session.signout.owned
texture.apply.bound_profile
texture.clear.bound_profile
```

封禁生效时不得自动删除：

```text
PermissionSubject
subject_roles
subject_permission_overrides
```

封禁与主体状态的区别：

| 状态 | 影响 |
| --- | --- |
| `banned_until > now` | 禁止加入服务器，不禁止 Yggdrasil 会话创建、刷新、校验、退出或材质写入 |
| `PermissionSubject.status = disabled` | 所有权限为空 |
| `PermissionSubject.status = locked` | 所有权限为空 |

管理员封禁操作必须检查：

```text
account.ban.any
```

管理员解封操作必须检查：

```text
account.unban.any
```

普通管理员不得封禁、解封、修改受保护主体所属账号。该限制不是权限短路，而是业务规则：目标用户主体 `protected = true` 时，操作 actor 必须具备 `permission_protected.manage.any`。

## 10. 权限判断接口

### 10.1 Require

输入：

```text
actor
permission_id
```

规则：

```text
actor.permissions contains permission_id
```

### 10.2 RequireScoped

输入：

```text
actor
permission_id
resource
```

规则：

```text
actor.permissions contains permission_id
AND resolver(permission.scope_id, actor, resource) == true
```

### 10.3 RequireAnyScoped

输入：

```text
actor
permission_ids[]
resource
```

规则：

```text
存在一个 permission_id：
  actor.permissions contains permission_id
  AND resolver(permission.scope_id, actor, resource) == true
```

### 10.4 Forbidden 语义

站内 API：

```text
非公开端点未认证 -> 401
公开端点无凭证 -> GuestActor
公开端点凭证无效 -> 401
权限不足 -> 403
私有资源不可见 -> 404
```

Yggdrasil API：

```text
无效 token / profile mismatch -> ForbiddenOperationException: Invalid token.
服务器加入链路账号封禁 -> ForbiddenOperationException: Account is banned. Please contact administrator.
权限不足 -> ForbiddenOperationException
```

`delegated_client_permissions` 表示客户端申请并允许使用的权限集合，不表示用户已经授权。该表保留历史命名，但不得把它理解为仅用于用户委托授权。公开应用不得申请 `server` scope。授权码和设备码流程必须在该集合基础上继续要求授权用户拥有对应权限，并拒绝 `server` scope；Client Credentials 流程必须在机密应用的该集合和 `client:{client_id}` 有效权限基础上按 app-only 会话策略发放 token。应用创建者权限变化后，不满足申请权限条件的 `pending` / `active` 应用必须被置为 `disabled`。

### 11.17 OAuth access token Redis 记录

OAuth access token 不是 PostgreSQL 表。用户委托 token 与 Client Credentials token 统一写入 Redis：

```text
oauth:access:{token_hash}
```

记录字段：

```text
token_hash
client_id
user_id       // 用户委托 token 才存在
grant_id      // 用户委托 token 才存在
permission_ids
expires_at
created_at
```

请求携带的 bearer token 必须先哈希再读取 Redis。Redis token 是短期凭证缓存，不是长期事实来源；用户授权、应用状态、应用权限主体和 refresh token 才是 PostgreSQL 事实来源。

```sql
    FOREIGN KEY(target_subject_id) REFERENCES permission_subjects(id) ON DELETE SET NULL,
    FOREIGN KEY(target_role_id) REFERENCES roles(id) ON DELETE SET NULL,
    FOREIGN KEY(target_permission_id) REFERENCES permissions(id) ON DELETE SET NULL,
    FOREIGN KEY(target_client_id) REFERENCES delegated_clients(id) ON DELETE SET NULL,
    FOREIGN KEY(target_grant_id) REFERENCES delegated_permission_grants(id) ON DELETE SET NULL
);
```

## 12. 权限计算

### 12.1 Subject Effective Permissions

计算公式：

```text
role_allow_bitset
| subject_allow_bitset
&^ subject_deny_bitset
```

计算步骤：

```text
1. 读取 permission_subjects。
2. status != active 时返回空集合。
3. 读取 subject_roles。
4. 读取 role_permissions。
5. 读取 subject_permission_overrides。
6. 按 permissions.bit_index 合并 role allow bitset。
7. 按 permissions.bit_index 合并 subject allow bitset。
8. 按 permissions.bit_index 移除 subject deny bitset。
9. 返回 subject effective bitset。
```

### 12.2 Actor Permissions

计算公式：

```text
subject_effective_bitset
& session_permission_bitset(session_kind, entrypoint)
& delegation_permission_bitset(delegation_id)
&^ account_sanction_denied_bitset(user_id, session_kind, entrypoint)
```

委托权限策略：

```text
delegation_id IS NULL：
  delegation_permission_bitset = all permission bits

delegation_id IS NOT NULL：
  delegated_permission_grants.status == active
  delegated_clients.status == active
  delegated_permission_grants.user_id == actor.user_id
  delegated_permission_grants.subject_id == actor.subject_id
  delegated_permission_grants.client_id == actor.delegated_client_id
  delegation_permission_bitset =
    delegated_client_permission_bitset(client_id)
    & delegated_grant_permission_bitset(grant_id)
```

委托访问不得读取 role_permissions，不得通过角色扩大权限。用户撤销授权、客户端禁用、用户权限 deny、角色权限变化都必须影响下一次 Actor 构造结果。

Client Credentials 权限策略：

```text
session_kind != client_credentials：
  client_credentials_permission_bitset = all permission bits

session_kind == client_credentials：
  redis oauth access token exists
  oauth_access_token.expires_at > now
  delegated_clients.status == active
  actor.subject_id == "client:" + oauth_access_token.client_id
  client_credentials_permission_bitset =
    client_subject_effective_permission_bitset
    & delegated_client_permission_bitset(client_id)
    & requested_token_scope_bitset
```

`requested_token_scope_bitset` 只能是客户端主体有效权限与应用已申请权限集合交集的子集。Client Credentials 不得读取用户 role，不得使用用户委托 grant，不得通过用户权限扩大客户端主体权限。

受保护管理者通过主体权限覆盖获得 `permission_protected.manage.any`，不通过角色获得全量权限。进入 Yggdrasil、Microsoft state 等受限入口时，仍然必须被 session policy 收窄。

## 13. 权限缓存

缓存键固定为：

```text
permission:subject:{subject_id}:effective
permission:actor:{session_kind}:{entrypoint}:{session_id}
permission:delegation:{grant_id}:effective
permission:client_token:{token_hash}:effective
permission:user:{user_id}:subject
```

必须失效的事件：

```text
permission_subjects.status 变化
subject_roles 变化
role_permissions 变化
subject_permission_overrides 变化
permissions 变化
permission_scopes 变化
session_permission_policies 变化
delegated_clients.status 变化
delegated_client_permissions 变化
delegated_permission_grants.status 变化
delegated_grant_permissions 变化
oauth_authorization_codes 创建、消费、过期
Redis OAuth access token 创建、删除、过期
oauth_refresh_tokens 创建、轮换、撤销、过期
users.banned_until 变化
用户密码修改
用户删除
Yggdrasil token 创建、刷新、删除
Yggdrasil token 绑定角色变化
Microsoft state 创建、消费、过期
```

缓存不是事实来源。数据库是唯一事实来源。

## 14. Service 层规范

受保护 service 方法签名必须包含 `PermissionActor`。

固定形式：

```go
func Operation(ctx context.Context, actor PermissionActor, input Input) (Output, error)
```

service 层流程固定为：

```text
1. 读取业务资源。
2. 资源不存在时返回业务定义的 not found。
3. 调用 Require / RequireScoped / RequireAnyScoped。
4. 权限通过后执行状态校验。
5. 执行数据库写入。
```

禁止形式：

```go
func Operation(ctx context.Context, userID string, isAdmin bool, input Input) (Output, error)
```

## 16. 开发者准则

权限系统由五个层次组成：

```text
PermissionSubject：长期权限身份
Subject Effective Permissions：主体长期有效权限
PermissionActor：会话入口下的实际权限身份
Delegation Permission Policy：委托访问的逐项权限收窄
Scope Resolver：资源级权限判定
```

`self` 和 `any` 不能覆盖站点需求。权限范围固定包含 `owned`、`bound_profile`、`public`、`assigned`、`server`、`system`。Yggdrasil 服务器登录 `join` 与 `hasJoined` 是权限控制的一部分。账号封禁通过会话入口策略移除服务器加入链路权限。外部 OIDC 身份和正版角色绑定复用用户主体，但保持独立资源、独立权限和独立 API；Microsoft 只是 provider adapter，不是权限绕过入口。委托访问使用逐项 Permission 授权，不得使用角色扩大权限。
